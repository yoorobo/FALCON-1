## 보고서 1: 두 문서의 정체와 SR과의 관계

### 1. `state_machine.md`
- **위임받은 SR 항목:** SR-13 (10개 상태 정의), SR-14 (전역 정지 전환), SR-15~SR-20 (상태별 전환 조건), SR-27 (자동 귀환 로직), SR-32~SR-33 (횡단 변수 `is_locked_return` 관리), SR-34~SR-36 (스태프 수동 처리 흐름)
- **이 문서에서 처음 정의된 참조 내용:** 전환 트리거 이름(`enter_tracking` 등), 이전 상태 추적을 위한 전역 변수(`previous_tracking_state`), `transitions` 라이브러리의 콜백 함수(`on_enter_*`), 상태보다 횡단 변수를 우선시하는 구체적인 분기 로직 코드(`get_led_color`).
- **SR만으로 구현 가능 여부:** 불가능. SR은 비즈니스 규칙("언제 무엇을 해라")만 담고 있으며, 이를 시스템 이벤트로 엮어내는 구체적인 트리거 이름, 콜백 매핑, 상태 복원 로직 등 코드 구조체 정보가 누락되어 있어 개발자 간 합의 및 실제 구현이 불가합니다.

### 2. `interface_specification.md`
- **위임받은 SR 항목:** SR-09 (인형 탐지 AI 통신), SR-37 (QR 스캔 파이프라인), SR-46, SR-50, SR-51 (웹/관제 실시간 통신 및 동기화).
- **이 문서에서 처음 정의된 참조 내용:** 내부 채널 레이블(A~H), 통신 프로토콜 명세(TCP/UDP/SocketIO/REST), 구체적 포트 번호(:8501, :8000, :5432 등), JSON 페이로드 키/값 스키마, ROS 2 토픽/서비스/액션명 및 메시지 타입(`std_msgs/String`, `nav2_msgs/action/NavigateToPose` 등), Protocol 기반 파이썬 인터페이스 클래스.
- **SR만으로 구현 가능 여부:** 불가능. SR에는 "TCP로 연결한다", "상태를 실시간 전송한다" 등의 High-level 규칙만 존재합니다. 각 모듈을 개발하는 인원들이 JSON 키 이름, 토픽명, 포트 번호 등 규격을 맞추지 않으면 시스템 통합 자체가 불가능합니다.

## 보고서 3: 우리 SR 가이드라인에 추가할 경계 원칙 (5개)

1. **상태머신과 비즈니스 로직의 분리**
   - **원칙:** 상태와 전환의 '비즈니스 조건(What/When)'은 SR에서 다루고, '콜백 함수, 내부 변수 유지, 전환 트리거 이름' 등 프로그래밍 구현체(How)는 상세설계로 전면 위임한다.
   - **ShopPinkki 근거:** SR-13은 상태 10개의 존재를 명시하나, `on_enter_LOCKED` 같은 콜백 로직은 `state_machine.md`에 분리됨.
   - **FALCON-1 주의점:** PFL 안전 모드나 공구 전달 모드의 조건은 SR에 적되, BT 노드나 State 콜백 함수명은 적지 않도록 주의.

2. **통신 규약의 상세화 위임**
   - **원칙:** SR에서는 '어떤 시스템 모듈과 어떤 목적으로 통신한다'만 명시하고, 포트 번호, 프로토콜 종류, 페이로드 JSON 스키마 등은 인터페이스 명세서(상세설계)로 위임한다.
   - **ShopPinkki 근거:** SR-46은 상태 정보 실시간 전송 사실만 적고, JSON 구조나 SocketIO 채널 규격은 `interface_specification.md`로 뺌.
   - **FALCON-1 주의점:** ROS 2 액션 메시지 구조나 음성 STT 페이로드 형식은 SR에 적지 않는다.

3. **사용자 인터페이스(UI/UX) 정책은 SR에 포함**
   - **원칙:** LED 색상 패턴, 음성 피드백 문구, 대시보드 표출 항목 등 최종 사용자가 직접 체감하는 인지적 정책은 기술적 구현이 아니므로 SR에 명시한다.
   - **ShopPinkki 근거:** SR-31에서 상태별 LED 색상표를 상세하게 명시함.
   - **FALCON-1 주의점:** 로봇의 음성 응답 문구("알겠습니다" 등)와 LED 패턴은 SR에 확정하여 표기.

4. **성능과 임계값(비기능 요구사항)은 SR의 몫**
   - **원칙:** 제어 주기(Hz), 배터리 방전 기준, 허용 오차 등 비기능적 수치와 임계값은 SR에서 명시하되 특정 모듈의 하드코딩된 '매직 넘버' 형태보다는 논리적 파라미터 기준으로 서술한다.
   - **ShopPinkki 근거:** SR-51의 1~2Hz 주기, SR-56의 배터리 20% 임계값 설정.
   - **FALCON-1 주의점:** 공구 전달 시 허용되는 팔 끝 속도 제한치(PFL 기준) 등은 SR에 명확한 수치로 규정해야 함.

5. **하드웨어/라이브러리/미들웨어 종속 기술 위임**
   - **원칙:** 시스템이 달성해야 할 동작 결과물은 SR에 쓰되, 이를 달성하기 위해 사용하는 특정 오픈소스 라이브러리 이름, 센서 제품명, ROS 2 전용 문법(`ROS_DOMAIN_ID`) 등은 상세설계로 위임한다.
   - **ShopPinkki 근거:** `interface_specification.md`에만 DDS QoS 설정(RELIABLE 등)이 명시됨.
   - **FALCON-1 주의점:** "오픈소스 MoveIt 2를 사용하여..." 대신 "역운동학 제어기를 이용하여..."로 SR을 작성.

## 보고서 4: ShopPinkki가 이 경계를 잘 못 지킨 사례

ShopPinkki SR 분석 중 식별된 기술 종속 및 상세설계 침범 사례는 **총 12건**입니다.

**기존 식별 8건:**
- SR-01: "ST7789, 2.4인치" (하드웨어 종속)
- SR-09: "TCP:5005", "UDP" (포트 및 프로토콜 종속)
- SR-10: "YOLOv8n", "Docker 컨테이너" (모델/런타임 종속)
- SR-11: "HSV 색상 히스토그램" (알고리즘 종속)
- SR-22: "P-Control" (제어 알고리즘 종속)
- SR-23: "RPLiDAR C1" (센서 모델명 종속)
- SR-37, SR-48: "OpenCV QRCodeDetector", "Web Speech API" (라이브러리/API 종속)
- SR-56: "pinkylib API", "20%" 매직넘버 (코드 레벨 명칭 및 매직넘버)

**추가 식별 4건 및 개선안:**
1. **SR-04:** `ROS_DOMAIN_ID=14`, `PINKY_ID` 환경변수 방식 명시 (미들웨어 환경변수 종속)
   - (개선) SR-04: "모든 로봇은 독립적인 네임스페이스를 가지며, 동일 네트워크에서 간섭 없이 통신 가능해야 한다. 미들웨어 설정 및 변수 구조는 인터페이스 명세 참조."
2. **SR-14:** `source='*'` 라는 Transitions 파이썬 라이브러리 전용 문법 명시 (구현 문법 종속)
   - (개선) SR-14: "배터리 잔량 부족 시 로봇의 현재 상태와 무관하게 즉시 정지 상태(HALTED)로 전환되어야 한다."
3. **SR-26:** `Nav2 Waypoint Navigation을 사용한다` (특정 프레임워크 플러그인 종속)
   - (개선) SR-26: "자율 주행 시나리오는 사전 정의된 목적지 좌표를 기반으로 한 경로 계획 및 주행 제어를 수행한다."
4. **SR-51:** `/robot_<PINKY_ID>/status` 토픽 이름 직접 명시 (인터페이스 명세 침범)
   - (개선) SR-51: "각 로봇은 중앙 관제 시스템에 상태 정보를 실시간(1~2Hz)으로 전송한다. 전송 규격과 식별자는 인터페이스 명세 참조."
