# FALCON-1 SR 작성 가이드라인 (System Requirements Authoring Guideline)

문서 버전:** v1.2 **최종 갱신:** 2026-05-05 **작성 목적:** FALCON-1 시스템 요구사항(SR) 작성 시 UR/SR/상세설계 간 역할과 경계를 명확히 하고, 기술 종속성을 피하며, 부가 상황을 빠짐없이 망라하기 위한 공식 기준.

## 변경 이력

- 

**v1.0 (Antigravity 자율 생성)**: 핵심 5원칙 + 정보 유형별 표 + 연계 문서 목록

- 

**v1.1 (보강)**: D1~D5 컨벤션, 5패턴, ShopPinkki 차용/극복, 작성 체크리스트 추가

- 

**v1.2 (현재, ID 단순화)**: 실무 사례 분석 결과 D4를 ShopPinkki 스타일로 단순화. 카테고리 문자·기능/비기능 구분자·분기 접미사 모두 제거하고 전역 일련번호(`SR-01`)로 통일. 표 섹션 제목이 분류를 담당.

## 1. 개요 및 설계 철학

FALCON-1 프로젝트의 요구사항 엔지니어링은 **"What(무엇을)"과 "How(어떻게)"를 엄격히 분리**하는 철학을 따릅니다.

- 

**UR (User Requirements):** 사용자 입장에서 시스템이 달성해야 할 **What** (비즈니스 목적)

- 

**SR (System Requirements):** 시스템 입장에서 그 What을 충족시키기 위한 정량적/논리적 기준과 예외 대응 시나리오 (**How+얼마나**의 논리적 아키텍처)

- 

**상세설계 (Design Docs):** SR을 실제 코드로 구현하기 위한 기술적 명세 (프로토콜, 코드, 변수명 등 완벽한 **How**)

본 가이드라인은 세 축으로 구성됩니다:

- 

**§2. 핵심 5대 작성 원칙** — 교수님 멘토링 기반 개념 원칙 (무엇을 SR에 쓰고 무엇을 위임할 것인지)

- 

**§3. 작성 컨벤션 D1~D5** — 실무 작성 규칙 (실제 SR을 어떤 형식·구조로 쓸 것인지)

- 

**§4. 부가 상황 망라 5패턴** — 원칙 4의 구체적 적용 방법론

## 2. 핵심 5대 작성 원칙

### 원칙 1: 상태머신과 비즈니스 로직의 분리

- 

**SR의 역할:** 로봇의 상태(모드) 이름, 각 상태로 전환되어야 하는 **비즈니스적 조건과 정책** 명시.

- 

**상세설계로 위임:** 실제 코드 레벨의 콜백 함수명(`on_enter_LOCKED` 등), 시스템 이벤트/트리거 이름, 특정 라이브러리(`transitions` 등)의 고유 문법(`source='*'`), 상태 우선순위를 제어하는 횡단 변수의 코드 구현 흐름.

- 

**예시:**

❌ (잘못된 예): `transitions 라이브러리의 source='*'를 활용해 배터리가 20% 이하일 때 HALTED로 전환한다.`

- 

✅ (올바른 예): `배터리 잔량이 위험 임계값 미만으로 저하될 경우, 현재 동작 모드와 무관하게 즉시 안전 대기 모드로 전환한다. (세부 제어는 state_machine.md 참조)`

### 원칙 2: 기술/프레임워크 종속 금지

- 

**SR의 역할:** 시스템이 달성해야 할 동작 결과 및 알고리즘의 **역할**을 서술.

- 

**상세설계로 위임:** 특정 오픈소스 패키지명(YOLOv8n, MoveIt 2), 센서 제품명(RPLiDAR C1), ROS 2 고유 환경변수(`ROS_DOMAIN_ID`) 등은 기재하지 않음.

- 

**예시:**

❌ (잘못된 예): `ROS 2 Nav2 Waypoint Navigation을 사용하여 목적지로 주행한다.`

- 

✅ (올바른 예): `사전 정의된 목적지 좌표를 향한 전역/지역 경로 계획 알고리즘을 수행하여 주행한다.`

### 원칙 3: 인터페이스 규약의 상세화 위임

- 

**SR의 역할:** 어떤 시스템 모듈과 **어떤 목적으로 통신하는지**, 그 주파수(Hz) 등 비기능적 요구사항 명시.

- 

**상세설계로 위임:** 포트 번호(`5005`, `8080`), 프로토콜 종류(`TCP`, `UDP`), JSON 페이로드 키 값, ROS 2 토픽/액션/서비스명 등 규격 명세는 **인터페이스 명세서(`interface_specification.md`)**로 전면 위임.

- 

**예시:**

❌ (잘못된 예): `관제 서버와 TCP 8080 포트를 통해 /robot_54/status 토픽으로 연결한다.`

- 

✅ (올바른 예): `각 로봇은 중앙 관제 시스템에 자신의 상태 정보를 실시간(1~2Hz)으로 전송해야 한다. (상세 규격은 인터페이스 명세서 참조)`

### 원칙 4: 부가 상황과 예외 분기 망라

- 

**SR의 역할:** UR에서 도출될 수 있는 모든 분기와 예외 상황(예: 네트워크 단절, E-stop 발동, 목표물 분실, 충돌 예상 등)에 대한 시스템적 대응 행동 시나리오를 SR 단계에서 **전부 커버**해야 함. 상세설계 단계에서 정책이 즉흥적으로 결정되는 것을 방지.

- 

**구체적 적용 방법:** §4 "부가 상황 망라 5패턴" 참조.

### 원칙 5: 사용자 접점(UI/UX) 정책은 SR에 명시

- 

**SR의 역할:** LED 색상표, 음성 피드백 출력 문구("알겠습니다"), 대시보드 표출 항목 등 **사용자가 직접 인지하는 정책**은 프로그래밍 구현법이 아니므로 반드시 SR에 구체적으로 확정하여 기재함.

## 3. 작성 컨벤션 D1~D5

핵심 5대 원칙이 "무엇을 SR에 쓸 것인지"라면, D1~D5는 "어떤 형식·구조로 쓸 것인지"의 실무 규칙입니다.

### D1. 이진 판정 가능성 원칙

- 

**규칙:** 모든 SR은 단일 기준으로 ✅(달성)/❌(미달)을 판정 가능해야 한다. 한 SR에 여러 독립 조건이 OR/AND로 묶여 있으면 **반드시 분리**한다.

- 

**이유:** 체크리스트 검증 시 "부분 달성"이라는 회색지대를 없애기 위함. (IEEE 29148이 요구하는 "singular" 속성과 같은 개념)

- 

**예시:**

❌ (잘못된 예): `SR-30: 통신 끊김, 배터리 부족, 위치 파악 불가 중 하나라도 발생 시 정지한다.` (3개 조건이 한 SR에 묶임 → 통신만 정상이고 배터리만 미구현이면 판정 불가)

- 

✅ (올바른 예): `SR-30: 통신 끊김 시 정지` / `SR-31: 배터리 임계 미만 시 정지` / `SR-32: 위치 추정 실패 시 정지` (3건의 **별개 SR로 분리 발행**)

### D2. 표 구조 표준화

- 

**규칙:** 모든 SR은 다음 3열 표 구조를 따른다.

| SR ID | 연관 UR | Description |

- 
**추가 컬럼 허용:** "상세설계 위임/참조" 컬럼은 부가 가능하나, 위 3열은 필수 고정.

- 

**이유:** ShopPinkki에서 검증된 `system_requirements_checklist.html` 도구가 이 3열 구조를 전제로 동작하므로, 향후 체크리스트 도구를 차용할 때(D5) 호환성 확보.

### D3. Description 라벨링

- 

**규칙:** Description 첫 부분에 다음 라벨 중 하나를 붙여 SR의 성격을 명시한다.

`(정상)` — 정상 흐름의 기본 동작

- 

`(예외)` — 정상 흐름에서 벗어난 상황의 시스템 대응

- 

`(전제)` — 기능이 동작하기 위한 사전 조건

- 

`(전역전환)` — 현재 모드와 무관하게 발생하는 강제 상태 전환

- 

`(알림)` — 사용자/관리자에게 전달하는 피드백·통지 정책

- 

`(전제조건)` — 기능이 "언제 안 되는지"의 부정적 전제 (ShopPinkki 패턴 E)

- 

**이유:** SR ID 자체가 단순 일련번호(D4)이므로, Description 첫머리 라벨이 **SR의 성격을 알리는 유일한 시각 단서**가 됩니다. 표 한 페이지에서 정상/예외 비율을 즉시 가늠 가능.

- 

**예시:**

`SR-01: (정상) PTT 마이크 입력 오디오는 지정된 명령 집합과 매칭되어야 하며...`

- 

`SR-03: (예외) 인지 신뢰도가 임계값 미만이면 어떠한 기계적 구동도 시작하지 않으며...`

- 

`SR-15: (전제) PTT 마이크 입력은 지정된 명령 집합이 사전 등록된 상태여야 한다.`

### D4. SR ID 네이밍 — 단순 일련번호

- 

**규칙:** 모든 SR은 `SR-NN`** 형식의 전역 일련번호**를 사용한다 (예: `SR-01`, `SR-02`, ..., `SR-56`).

**카테고리 문자 사용 금지** — 카테고리(A/B/C/D/E/F)는 표의 **섹션 제목**에서만 표현하고 ID에는 묻지 않는다.

- 

**기능/비기능 구분자 사용 금지** — 기능/비기능 구분도 표 섹션 제목으로 표현 (예: `## A. 호출 & 통신 (기능)` vs `## NF. 비기능`)

- 

**분기 접미사(a/b/c) 사용 금지** — D1으로 분기를 분리할 경우 **별개 일련번호로 발행** (예: `SR-30, SR-31, SR-32`로 3건 발행)

- 

**순번은 0-padding 2자리 권장** (`SR-01` ~ `SR-99`). 100건 초과 시 자연스럽게 3자리로 확장.

- 

**이유:**

**실무 사례 일치** — Robot Framework reqcov(`REQ-001`), 자동차 FMEA(`FR-1`), ShopPinkki(`SR-01`) 모두 단순 일련번호 사용. IEEE 29148도 ID 형식은 자유로 두고 "고유성·추적성"만 요구.

- 

**회의에서 입으로 부르기 좋음** — "에스알 영삼" vs "에스알 에프이 영삼 에이". 짧고 기억하기 쉬운(memorable) ID가 산업 best practice.

- 

**DRY 원칙** — 표 섹션 제목이 이미 카테고리/기능 구분을 시각화하므로 ID에 동일 정보를 묻는 것은 중복.

- 

**추적성은 매트릭스가 담당** — 어차피 IEEE 29148이 traceability matrix를 별도로 요구하므로, ID에 카테고리를 박을 필요가 없음.

- 

**추적성 보완:** SR이 어느 카테고리·UR에 속하는지는 (a) 표 섹션 제목, (b) "연관 UR" 컬럼, (c) 별도 traceability matrix가 함께 보장.

### D5. 체크리스트 도구 차용

- 

**규칙:** SR 작성 완료 후 ShopPinkki의 `system_requirements_checklist.html`을 차용하여 진행률·달성률을 추적한다.

- 

**호환성 조건:** D2의 3열 구조 + D4의 단순 일련번호(`SR-NN`)를 따라야 도구가 정상 동작 (ShopPinkki 도구가 이 형식을 전제로 만들어졌음).

- 

**시점:** SR이 안정화된 이후 도입 (PoC Must 전 건이 1차 작성된 시점).

## 4. 부가 상황 망라 5패턴 (원칙 4 적용 방법)

원칙 4("부가 상황과 예외 분기 망라")의 추상적 지시를 구체적 SR로 펼치는 5가지 패턴입니다. ShopPinkki SR 분석에서 도출되었습니다.

**

📌 ID 표기 안내**: 아래 예시의 `SR-NN` 번호는 **설명용 가상 번호**입니다. 실제 작성 시에는 본인 문서의 다음 일련번호를 부여하세요.

### 패턴 A. 한 UR을 여러 분기 SR로 펼침

- 

**언제:** 한 UR이 정상 흐름 + 1개 이상의 예외 흐름을 포함할 때.

- 

**방법:** 정상 흐름 SR + 각 예외 SR을 **각각 별개 일련번호로 발행**.

- 

**ShopPinkki 사례:** UR-14(배터리) → SR-14(임계 도달 시 자동 귀환) + SR-28(귀환 중 배터리 추가 저하) + SR-34(스태프 수동 충전) + SR-56(임계값 정의) **= 4건의 별개 SR**

- 

**FALCON-1 적용 후보:**

UR_C01(공구 꺼내기) → 정상 파지 SR + 파지 실패 SR + 슬롯 미식별 SR (3건의 별개 SR)

- 

UR_D04(외부 당김 인지) → 정상 릴리스 SR + 임계값 미만 시 유지 SR + 과도한 외력 시 비상 정지 SR (3건의 별개 SR)

### 패턴 B. 보안/차단 상황을 별도 SR로 격상

- 

**언제:** "이런 입력은 거부한다", "이런 영역은 들어가지 않는다" 같은 **부정적 정책**이 UR에 묻혀 있을 때.

- 

**방법:** 거부·차단 정책 자체를 독립 SR로 분리 (별개 일련번호).

- 

**ShopPinkki 사례:** SR-07(인증 차단), SR-16(잠금 상태 차단), SR-17(허용 영역 외 차단) **= 3건의 별개 SR**

- 

**FALCON-1 적용 후보:**

UR_E07(운용 환경 제약) → 맵 외 목표 거부 SR + 비인가 네트워크 차단 SR (현재 SR_E07이 이를 한 줄에 묶고 있음 → D1 위반)

- 

UR_C06(미등록 공구 호출) → 미등록 공구 호출 거부 SR

### 패턴 C. 횡단 변수·플래그를 별도 SR 묶음으로

- 

**언제:** 여러 SR에 걸쳐 영향을 주는 상태 플래그가 존재할 때.

- 

**방법:** 플래그의 정의 SR + 영향 SR들을 명시적으로 묶음 (별개 일련번호들로 발행).

- 

**ShopPinkki 사례:** `is_locked_return` 플래그 → 5개 SR이 이 플래그를 참조

- 

**FALCON-1 적용 후보:**

`is_arm_locked` (주행 중 팔 잠금 플래그) — 정의 SR + 이를 참조하는 SR들 (예: 추종 중 팔 잠금, 매니퓰레이션 모드 진입 조건, 안전 자세 강제)

- 

`is_handover_active` (핸드오버 진행 중 플래그) — 정의 SR + 핸드오버 안전 정책 SR들이 참조

- 

각 플래그의 **정의·생성·해제 시점**을 별도 SR로 명시 (코드 구현이 아니라 비즈니스 정책 레벨에서)

### 패턴 D. 동일 분기를 두 진입 경로에 SR 분리

- 

**언제:** 같은 결과 동작이 여러 진입점(능동/자동, 수동/원격 등)에서 트리거될 때.

- 

**방법:** 각 진입점별로 SR을 분리해 트리거 조건 명시 (별개 일련번호).

- 

**ShopPinkki 사례:** SR-18(능동 잠금) vs SR-19(자동 잠금) — 결과는 같지만 트리거가 다름.

- 

**FALCON-1 적용 후보:**

UR_E02(E-stop) → 본체 버튼 SR + 작업자 무선 리모컨 SR + 안전관리자 무선 리모컨 SR (3 진입점, 현재 SR_E02가 한 줄에 묶음 → D1 위반)

- 

UR_D05(공구 회수) → 트레이 거치 회수 SR + 직접 손 회수 SR

### 패턴 E. "언제 안 되는지"의 전제 조건 명시

- 

**언제:** 기능이 "특정 조건 하에서만" 동작 가능한데, 그 조건이 UR에 함의로만 존재할 때.

- 

**방법:** Description 첫머리에 `(전제)` 또는 `(전제조건)` 라벨로 부정적 전제를 명시 SR화 (별개 일련번호로 발행).

- 

**ShopPinkki 사례:** SR-21, SR-39, SR-45 — "X가 ~이 아닐 때만 Y가 동작한다"

- 

**FALCON-1 적용 후보:**

`(전제)` 베이스 주행 속도가 0이 아닐 때는 매니퓰레이션 모드 활성화를 시도하지 않는다.

- 

`(전제)` 작업자 손 제스처가 감지되지 않으면 핸드오버 동작을 개시하지 않는다.

## 5. ShopPinkki에서 차용할 좋은 패턴 / 극복할 잘못된 패턴

ShopPinkki는 모방 대상이 아니지만, 잘한 부분과 잘못한 부분을 분리해 학습합니다.

### 5.1 차용할 좋은 패턴

| 항목 | ShopPinkki 사례 | FALCON-1 적용 |
|---|---|---|
| **부가 상황 망라** | §4의 5패턴 전부 | §4 그대로 적용 |
| **3열 표 구조** | `system_requirements.md` 전체 | D2로 명문화 |
| **단순 일련번호 ID** | `SR-01`~`SR-56` | **D4로 명문화** (v1.2에서 회귀) |
| **체크리스트 도구** | `system_requirements_checklist.html` | D5로 차용 |
| **상태별 LED·음성 정책 SR화** | SR-31 (LED 색상표) | 원칙 5로 명문화 |
| **상세설계 위임 컬럼** | "상세설계 위임/참조" 컬럼 | 본 가이드라인 채택 |

### 5.2 극복할 잘못된 패턴 (원칙 2·3 위반 12건)

ShopPinkki SR에 박힌 기술 종속 사례. FALCON-1은 동일 함정을 회피해야 합니다. 상세 분석은 `_analysis/shoppinkki_design_boundary_analysis.md` 참조.

- 

하드웨어 모델명: SR-01("ST7789, 2.4인치"), SR-23("RPLiDAR C1")

- 

포트·프로토콜: SR-09("TCP:5005", "UDP")

- 

모델·런타임명: SR-10("YOLOv8n", "Docker")

- 

알고리즘명: SR-11("HSV 색상 히스토그램"), SR-22("P-Control")

- 

라이브러리·API명: SR-37("OpenCV QRCodeDetector"), SR-48("Web Speech API"), SR-56("pinkylib API")

- 

환경변수: SR-04(`ROS_DOMAIN_ID=14`)

- 

라이브러리 문법: SR-14(`source='*'`)

- 

프레임워크 플러그인: SR-26("Nav2 Waypoint Navigation")

- 

토픽명 직접 노출: SR-51(`/robot_/status`)

→ FALCON-1은 이들을 모두 상세설계 문서로 위임.

### 5.3 매직넘버 처리 정책 (ShopPinkki와 차별화)

ShopPinkki는 매직넘버(SR-56의 "20%" 등)를 SR 본문에 직접 박았습니다. FALCON-1은 다음 정책을 채택합니다:

- 

**본문에 직접 표기 허용:** SR Description에 `(예: 250mm/s 이하)` 형태로 부기.

- 

**단, 별도 임계값 표 권장:** SR 문서 말미에 "임계값 파라미터 표"를 두고, 본문은 `임계값 P-D02` 같은 참조로 대체하면 더 좋음.

- 

**이유:** 임계값은 PoC 결과에 따라 자주 바뀌는 비기능 파라미터이므로, 본문 수정 없이 표만 갱신할 수 있도록 분리하는 편이 유지보수상 유리.

## 7. FALCON-1 필수 연계 상세설계 문서 목록

SR 작성 시 아래 문서들을 "상세설계 위임/참조" 컬럼에 명시하여 기술 종속성을 피합니다.

- 

`system_architecture.md` (SA): 시스템 전체 모듈 분해 및 데이터 흐름

- 

`interface_specification.md` (IS): ROS 통신, 음성 채널 규격, 프로토콜 및 토픽명

- 

`erd.md` (ERD): 공구 데이터 및 로그 스키마 명세

- 

`state_machine.md` (SM): 상태 전환 테이블, 횡단 변수 조건 로직

- 

`safety_pfl_spec.md` (PFL): ISO 10218-2 안전 기준 기반 속도/힘 제한 로직

- 

`manipulation_sequence.md` (MS): 양팔 협동 궤적, 입출고/전달 세부 파이프라인

- 

`behavior_tree.md` (BT): 복합 장애 상황, 임무 실패 재시도 흐름

(작성 순서는 인계서 §11 권고: SA→IS→ERD→SM→PFL→MS→BT)

## 8. SR 작성 체크리스트 (작성자용)

각 SR을 발행하기 전에 다음을 자체 점검합니다.

- 

[ ] **D1**: 이 SR이 하나의 기준으로 ✅/❌ 판정 가능한가? 복합 조건이면 별개 SR로 분리했는가?

- 

[ ] **D2**: 3열 표 구조(`SR ID | 연관 UR | Description`)를 따랐는가?

- 

[ ] **D3**: Description 첫머리에 `(정상)`/`(예외)`/`(전제)` 등 라벨이 있는가?

- 

[ ] **D4**: ID가 단순 일련번호 `SR-NN` 형식인가? (카테고리 문자, 기능/비기능 구분자, a/b/c 접미사 모두 사용 안 함)

- 

[ ] **원칙 1**: 콜백 함수명, 트리거 이름, 라이브러리 문법이 본문에 박혀있지 않은가?

- 

[ ] **원칙 2**: 라이브러리·센서·모델명·환경변수가 본문에 박혀있지 않은가?

- 

[ ] **원칙 3**: 포트, 프로토콜, JSON 키, 토픽명이 본문에 박혀있지 않은가?

- 

[ ] **원칙 4 / §4 5패턴**: 이 UR의 부가 상황(예외, 분기, 전제)이 별개 SR로 펼쳐졌는가?

- 

[ ] **원칙 5**: UI/UX 정책(LED 색상, 음성 문구)이 SR에 구체적으로 명시되었는가?

- 

[ ] **상세설계 위임 컬럼**: 본 SR이 어느 상세설계 문서에서 구체화되는지 표시되었는가?
